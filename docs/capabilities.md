# Current capabilities and verification boundaries

This is an inventory of the current implementation, not a claim to implement every capability in the [44-item research catalog](research/02-capability-catalog.zh-Hant.md).

| Area | Available in this build | Limits / unavailable |
| --- | --- | --- |
| CPU | OS-reported model, overall and per-logical-core usage; recent history and range; manual integer check against a fixed known answer. | Up to eight worker threads; one small computation cannot certify all instructions or cores. No independent physical-core mapping. |
| Memory | OS-reported total, used and available; history; allocated-memory alternating-pattern readback. | At most 256 MiB and one quarter of available memory; no full-RAM, ECC, SPD, or boot-time test. |
| GPU | One preferred wgpu backend is enumerated; select its retained adapter for a small verified compute check. Optional NVML provides NVIDIA load, temperature, VRAM, graphics clock, power, intended fan-0 speed and driver version if supported. An Adapter capabilities section shows backend, PCI vendor/device IDs, maximum 2D texture, compute workgroup dimensions, storage-buffer binding and optional feature count. | Software adapters are unavailable for testing; no full GPU or VRAM stress test. AMD/Intel load, VRAM and temperature are not supplied by this build. macOS may show unassociated raw IORegistry utilization keys; their meanings and availability vary by driver. A unique name match with NVML is heuristic; ambiguous matches stay separately labelled. Hardware hot-plug needs restart. |
| Hardware pages | CPU, GPU, memory and storage pages each include a matching bounded check and recent results; motherboard ("Parts & board"), drivers, network/Wi-Fi and Bluetooth have dedicated views. Parts & board adds CPU-Z-style processor description/instruction sets/virtualization/processor ID, per-slot memory voltage and bus widths, GPU driver/BIOS/VRAM/PCI/display mode and EDID-decoded attached displays. The Drivers page lists OS driver-store records with class, version, provider and signature, filterable by name/class. | macOS may provide a board ID; motherboard model and dedicated board, Wi-Fi and Bluetooth stress tests are unavailable. Chipset/VRM sensors and GPU clocks need a vendor driver. The driver inventory is a read-only OS report, not an update tool or a correctness check. An optional four-attempt TCP connection check is available for a user-entered numeric endpoint; it does not measure Wi-Fi throughput. macOS Bluetooth controller status can be checked again manually, and Wi-Fi interface mapping is collected at startup, when provided by OS tools; connected-device names are shown when reported, but wireless signal quality is unavailable. |
| Processes and network | Search processes by name/PID and sort CPU or memory; show per-interface network rates from measured byte deltas. | OS permissions can limit results; CPU can exceed 100%; network interfaces may include virtual devices and zero can mean unavailable. No process controls or GPU attribution. |
| Frame analysis | Import one-process, one-swap-chain PresentMon CSV and calculate displayed FPS and frame-time statistics. | Offline only; requires displayed-frame timing columns. Multi-process or multi-swap-chain files are rejected. Hardware Hub does not capture live FPS. |
| Floating monitor | Optional always-on-top desktop window with CPU and memory and stale status. | Full-screen in-game overlay and FPS are unavailable; window-manager behavior varies. |
| Sensors (temperature, fan) | macOS reads the SMC directly, exposing the per-subsystem temperature keys (CPU proximity/die, GPU, battery, memory, heatsink) plus `F0Ac`-style fan keys when present. Every row shows current, session minimum and session maximum, and min/max can be cleared from the UI. Windows reads the ACPI thermal zones from the `Thermal Zone Information` performance counters (`Win32_PerfRawData_Counters_ThermalZoneInformation`, readable as a standard user) and falls back to `MSAcpi_ThermalZoneTemperature` in `ROOT\WMI` when available (elevated). Linux falls back to `sysinfo` components. A selectable temperature graph keeps up to 60 batches, shows min/max/average and gap-aware segments, and exports one sensor to CSV. Advisory threshold alerts support warning/critical severity, a configurable hold time, fresh-sample checks and acknowledgement. | Values are firmware readings, not calibrated probes; unreadable keys are omitted (plausibility range applied) rather than shown as 0. Fan rows appear only when the firmware exposes per-fan keys; Windows exposes no fan-speed source. Voltage and power SMC keys are not displayed because their meaning is model-specific. Windows ACPI zones are coarse firmware values, not per-core die temperature; a machine whose firmware exposes no zone shows an explanatory note instead of a value. No per-sensor timestamp, no automatic shutdown; alerts never change fan speed, clocks or tests. |
| Storage | Mounted-volume capacity, kind and OS counters when exposed; bounded owned-file write/readback verification, configurable 1–1024 MiB total write cap, default 64 MiB. | A volume is not necessarily a physical drive. macOS provides an OS-reported SMART summary where exposed; raw SMART attributes are available only through optional imported smartctl JSON; no guaranteed physical-drive mapping, raw disk test, or reproducible storage benchmark. Readback can come from cache; writes cause wear. |
| Workflow | One manual test at a time, start/stop (button or Esc), determinate progress with percent and estimated time left, quick-duration presets (15 s / 1 min / 5 min), typed result status and a plain-language verdict, and session reports in text or JSON with settings and system context. During a run the current panel shows live CPU/memory load, the highest temperature with a safety label, a temperature sparkline, work units/phase/throughput and a live error count. Memory offers four deterministic byte patterns, disk three and GPU three intensity levels; mismatches are reported with location, expected and actual values (first eight stored, all counted). An opt-in checkbox stops only the software check at the advisory temperature limit; it never changes hardware. CSV can export the most recent 60 CPU/memory samples, one selected temperature series, or a bounded session log. Telemetry cadence is adjustable from 250–5000 ms. A CPU-Z/GPU-Z-style system report exports the specification sheet and current sensors as text or JSON with optional redaction of serials, paths and device names. Cmd/Ctrl+1–9 switch pages. | A **Combined CPU + memory** check runs those two bounded workers concurrently with one merged progress and error readout; it is the only multi-subsystem load and remains a correctness check, not a power-supply/voltage certification. With two or more results, the Reports page offers a side-by-side **Compare runs** view (status, verified units, errors, elapsed, settings) for this session only. | No automatic thermal shutdown of the machine, scheduling, full four-subsystem (CPU+GPU+RAM+PSU) simultaneous load, or comparable benchmark scores. The alert, peak label and auto-stop are advisory and never change hardware behaviour; a machine with no reported sensor shows "no sensor" rather than a fabricated value. Selected patterns are deterministic data patterns, not the full algorithm suites of MemTest86/Prime95; these remain bounded correctness checks, not exhaustive burn-in. System reports are a snapshot of OS-reported inventory, not validated hardware data; no online validation or upload. Disk/driver operations can delay cancellation. Reports may contain paths and hardware details unless redaction is enabled. |
| Specification sheet (Details) | CPU identity, vendor, architecture, socket, stepping, physical/logical and Apple-silicon P/E cores, reported clocks, L1/L2/L3 and cache line; memory modules with type, rated and firmware-configured speed, form factor, manufacturer, part number and serial; GPU driver build, driver date and current display mode; wgpu adapter driver and vendor/device IDs plus OS-reported VRAM and API; per-volume S.M.A.R.T. state, protocol and solid-state flag; NVMe model, firmware, link width/speed and TRIM; model identifier, OS, kernel, firmware, uptime and battery state. | Collected once at startup. macOS uses read-only `sysctl`, `system_profiler`, `diskutil` and `pmset`; Windows uses one read-only `powershell -NoProfile` pass over CIM/WMI (model, firmware, board, memory modules, rated clock, L2/L3, drive model and OS health, volume health, battery, Wi-Fi interface, Bluetooth controller); Linux falls back to `sysinfo` alone. Windows does not report L1 cache sizes, cache line, or a per-core clock. Optional local smartctl JSON import displays ATA attributes and selected NVMe fields; it is not live, and its source is not verified. No SMC voltage or power values, no SPD timing profiles. Values are OS-reported, not a hardware diagnosis. |

GPU selection and actual NVML/temperature support depend on the host. The current Linux cloud validation has no physical GPU and no reported system temperature sensors; it cannot establish Windows hardware support. The cross-target check and Windows CI build are compilation/test evidence, not real Windows hardware execution.

## Linux cloud functional checks

The following checks were performed against the Linux cloud environment with a software Xorg display. They demonstrate the listed flows on that environment, not all hardware combinations.

| Flow | Observed result |
| --- | --- |
| Overview | Real CPU, memory and volume data appeared; one llvmpipe adapter was shown; the unavailable system-temperature state was explicit. History reset cleared the chart. |
| CPU | Started, showed progress, stopped, then restarted and completed after a one-second run. The headless smoke run also stopped and restarted it. |
| Memory | A 64 MiB GUI run completed; the headless smoke used 1 MiB. Both verified completed pattern passes. |
| File I/O | A GUI run wrote and verified 1 MiB under a 1 MiB total cap. Its owned scratch file was removed and a pre-existing sentinel remained unchanged; an invalid directory produced Failed. |
| GPU | The GUI selected the software adapter and reported Unavailable. No physical GPU compute, NVML device, or multi-GPU machine was available. |
| Reports | GUI exported text and JSON; a second export to the same JSON path was rejected and its content hash remained unchanged. Automated tests also verify relevant fields and no-overwrite behavior. |

Run `cargo test --locked` for the unit suite, or `cargo run --locked --example smoke` for a bounded headless run. The smoke run allocates 1 MiB for memory, writes at most 1 MiB to its own temporary directory, performs short CPU checks, and verifies the unavailable GPU path without launching a GPU workload.

## macOS functional checks (2026-11-17)

On the Intel macOS development machine, the app was opened and the hardware pages, CPU/GPU/memory/storage layouts, process search, floating window, Bluetooth controller refresh, network diagnostic, SMART JSON import and PresentMon CSV analysis were visually inspected. The network diagnostic completed four connections to a local test listener. A one-second Metal GPU compute check completed 43 verified dispatches; an in-flight dispatch was reported as unverified. This is a small compute correctness check, not a full GPU or VRAM stress test. A locally initiated sensor log wrote eight batches and stopped with zero drops. Unit tests and the bounded headless smoke check also passed.

These checks cover this Mac and selected flows, not every combination of hardware, operating system or driver. Imported SMART and PresentMon test files were fixtures, not live drive or game measurements. Wi-Fi radio tests, Bluetooth stress, board stress, live game capture, game overlays, Windows hardware and Apple silicon hardware remain unverified or unavailable as described above.
